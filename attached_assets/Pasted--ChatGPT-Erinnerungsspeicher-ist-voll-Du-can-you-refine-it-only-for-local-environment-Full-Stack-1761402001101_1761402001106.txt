Project Overview
Build a local observability platform using OpenTelemetry Helm charts that automatically export to ClickHouse. All components except the frontend run inside Kubernetes via Helm. The React UI runs outside the cluster as a standalone application.
Architecture Components
1. Gateway Service (NestJS) - IN HELM
Purpose: API gateway that generates observability data
Responsibilities:

Expose REST endpoint that returns dummy data
Auto-instrument with OpenTelemetry SDK
Export traces, spans, and logs via OTLP protocol to OTel Collector
Generate realistic trace hierarchies with multiple spans
Include structured logging with trace correlation

Deployment:

Runs as Kubernetes Deployment via Helm
Exposed via Kubernetes Service (ClusterIP)
Port-forwarded for external client access
Accessible at http://localhost:3000 (via port-forward)

Configuration Needs:

OTLP endpoint pointing to OTel Collector service (internal DNS)
Service name identification
Auto-instrumentation for HTTP

2. OpenTelemetry Collector (Official Helm Chart) - IN HELM
Purpose: Central telemetry pipeline
Responsibilities:

Receive OTLP data (gRPC and HTTP protocols)
Process data (batching, filtering, enrichment)
Export directly to ClickHouse using built-in ClickHouse exporter
Auto-create ClickHouse tables with proper schema
Handle retries and queuing

Deployment:

Installed as sub-chart dependency
Runs as Kubernetes Deployment
Internal service for Gateway and Backend communication
No external access needed

Configuration Needs:

OTLP receivers (gRPC on port 4317, HTTP on port 4318)
Batch processor for performance
Memory limiter to prevent overload
ClickHouse exporter with internal service DNS
Auto-schema creation enabled
Data retention TTL settings

3. ClickHouse Database (Official Helm Chart) - IN HELM
Purpose: Time-series storage for all telemetry
Responsibilities:

Store traces with full span hierarchy
Store logs with trace correlation
Provide fast time-range queries
Handle high write throughput
Auto-partition by date
Auto-expire old data based on TTL

Deployment:

Installed as sub-chart dependency
Runs as Kubernetes StatefulSet
Persistent volume for data storage
Internal service for OTel Collector and Backend
Optionally port-forwarded for direct access/debugging

Configuration Needs:

Persistent volume for data storage

Native protocol port (9000) for OTel Collector
HTTP interface port (8123) for Backend API
Database name (e.g., "observability")

Note: OTel Collector creates tables automatically with proper:

Trace fields (TraceId, SpanId, ParentSpanId, Duration, Status, etc.)
Log fields (Timestamp, Severity, Body, TraceId, etc.)
Optimized indexes and compression
Partitioning strategy
TTL policies

Poll ClickHouse for new data and push to connected clients
Enable CORS for external frontend access

Deployment:

Port-forwarded for frontend access

API Endpoints:

Retrieve service-level metrics
SSE stream for live updates

Configuration Needs:

ClickHouse connection via internal service DNS
CORS configuration allowing localhost origins
Environment variables for database credentials
Health check endpoints for Kubernetes probes

Real-time Strategy:

Poll ClickHouse every few seconds for recent data
Detect new traces/logs since last check
Broadcast updates via SSE to all connected UI clients
Support multiple concurrent SSE connections
